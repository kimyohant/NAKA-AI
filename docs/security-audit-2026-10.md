## ข้อค้นพบ

### 1. ชำระเงินแพ็กเกจเดียวกันพร้อมกันแล้วเสียระยะเวลาที่ซื้อหนึ่งรายการ

- **ความรุนแรง:** สูง — ลูกค้าจ่ายเงินจริงสองครั้ง แต่ได้รับอายุแพ็กเกจเพียงหนึ่งรอบ
- **ตำแหน่ง:** `src/billing/index.ts:52-55`, `src/billing/index.ts:61-74`
- **สถานะ:** ยืนยันในเครื่อง
- **ขั้นตอนที่ทำให้เกิดปัญหา:** ให้ผู้ใช้ที่ยังไม่มี subscription เปิด Checkout สองรายการสำหรับแพ็กเกจ `pro` รายเดือนและชำระทั้งคู่ ให้ webhook/การ polling สองคำขอเข้า `applyPayment` พร้อมกันจนทั้งคู่ `SELECT subscriptions` ก่อนคำขอแรกบันทึกผล ทั้งคู่จึงได้ `extending=false` จากนั้น D1 เรียง `batch` ทั้งสองรายการ ผลจำลอง: `payments` ทั้ง `p1` และ `p2` เป็น `successful` แต่ `subscriptions.expires_at` อยู่ประมาณ 30 วันจากปัจจุบัน แทนที่จะเป็น 60 วัน เพราะ `ON CONFLICT` ของคำขอที่สองตั้งค่า `?6 + ?7` อีกครั้ง
- **วิธีแก้ที่แนะนำ:** ย้ายการตัดสินใจว่าจะต่ออายุเข้า SQL ภายในธุรกรรมเดียวกับการ claim payment โดยเทียบ `subscriptions.plan_id/status/expires_at` ณ เวลาที่ `UPSERT` ทำงาน และบวกอายุจากวันหมดอายุล่าสุดเมื่อเป็นแพ็กเกจเดียวกันที่ยังใช้งานอยู่ เพิ่มเทสสอง payment ที่ apply พร้อมกันและยืนยันอายุรวมสองรอบ

### 2. คำขอลิงก์รีเซ็ตรหัสผ่านพร้อมกันข้าม limit ต่ออีเมล/IP ได้

- **ความรุนแรง:** ปานกลาง — สามารถส่งอีเมลรีเซ็ตเกิน 3 ครั้งต่ออีเมลหรือสร้างแถวเกิน 10 ครั้งต่อ IP ในชั่วโมงเดียว
- **ตำแหน่ง:** `src/auth/password.ts:226-246`
- **สถานะ:** ยืนยันในเครื่อง
- **ขั้นตอนที่ทำให้เกิดปัญหา:** ส่ง `POST /api/auth/password/forgot` หกคำขอพร้อมกันจาก IP เดียวไปยังอีเมลเดียวกัน โดยเริ่มก่อนมีแถวใน `auth_password_resets` ทุกคำขออ่าน `COUNT(*)` ก่อนมีการ `INSERT` แล้วแต่ละคำขอผ่านเงื่อนไข limit ผลจำลองด้วย handler จริงและการเรียง `batch`: ทั้งหกคำขอสำเร็จและเกิดหกแถว ขณะที่การส่งทีละคำขอครั้งที่สี่ได้ 429 ตามเทสปัจจุบัน หากใช้บัญชีจริง คำขอที่รับเพิ่มยังสามารถเรียกผู้ให้บริการอีเมลและทำให้ลิงก์ก่อนหน้าใช้ไม่ได้
- **วิธีแก้ที่แนะนำ:** ตรวจโควตาและบันทึกการใช้โควตาในคำสั่งเขียนเดียวหรือธุรกรรมเดียวที่มีเงื่อนไข SQL ตรวจนับ ณ เวลาที่เขียน แล้วส่งอีเมลเฉพาะเมื่อ claim สำเร็จ เพิ่มเทส concurrency หลายคำขอบน D1 จริงและตรวจจำนวนแถว/อีเมล

### 3. Worker ที่ lease หมดแล้วเขียนผลทับ attempt ใหม่ได้

- **ความรุนแรง:** ปานกลาง — ผลงานที่คิดเครดิตอาจเป็นผลจาก attempt เก่า และงานอาจถูกประมวลผลซ้ำโดยผู้ให้บริการ
- **ตำแหน่ง:** `src/jobs.ts:90-109`, `src/jobs.ts:119-149`, `src/jobs.ts:186`
- **สถานะ:** ยืนยันในเครื่อง
- **ขั้นตอนที่ทำให้เกิดปัญหา:** ให้ worker A claim งาน (`attempts=1`) แล้วค้างจน `lease_until` หมด จากนั้น `recoverExpiredLeases` นำงานกลับคิวและ worker B claim (`attempts=2`) ขณะ B ยังทำงาน ให้ A เรียก `completeJob(jobId, outputA)` เพราะ `UPDATE` ตรวจเพียง `id` กับ `status='running'` จึงเปลี่ยนงานของ B เป็น `done` ด้วย `outputA`; B เรียก `completeJob(..., outputB)` ภายหลังแล้วเขียนไม่ได้ ผลจำลองสุดท้ายคือ `attempts=2` แต่ `output` เป็นของ A เส้นทาง `failJob` ของ A มีเงื่อนไขหลวมแบบเดียวกัน
- **วิธีแก้ที่แนะนำ:** ใช้ fencing token หรือเลข attempt จาก `claimNextJob` ส่งต่อถึง `completeJob`/`failJob` และกำหนด `WHERE id=? AND status='running' AND attempt/token=?` ตรวจ `meta.changes` ก่อนถือว่าสำเร็จ เพิ่มเทสที่ปล่อย A ทำงานข้าม lease แล้วให้ B claim ก่อน A จบ

### 4. Webhook อ่าน request body ทั้งก้อนก่อนตรวจขนาด

- **ความรุนแรง:** ปานกลาง หาก request ขนาดใหญ่ทำให้ Worker ใช้หน่วยความจำ/เวลาเกินขีดจำกัด
- **ตำแหน่ง:** `src/billing/index.ts:223-225`
- **สถานะ:** ยังไม่ยืนยันผลกระทบบน Cloudflare production
- **ขั้นตอนที่ทำให้เกิดปัญหา:** ส่ง `POST /webhook/stripe` ที่ body ใหญ่กว่า 256 KiB และไม่มีลายเซ็นที่ถูกต้อง ในโค้ด `await request.text()` จะอ่าน body ทั้งหมดก่อนตอบ 413 และก่อนตรวจลายเซ็น จึงใช้ทรัพยากรตามขนาด body ที่แพลตฟอร์มยอมรับ ยังไม่ได้ยิงคำขอขนาดใหญ่หรือวัดหน่วยความจำบน Worker จริง
- **วิธีแก้ที่แนะนำ:** ปฏิเสธ `Content-Length` ที่เกิน limit ตั้งแต่ต้นเมื่อมี header และอ่าน stream โดยนับ **bytes** พร้อมหยุดทันทีเมื่อเกิน 256 KiB โดยคง raw bytes สำหรับการตรวจลายเซ็น

### 5. Error จากงานอาจพาข้อมูลลูกค้าเข้า log

- **ความรุนแรง:** ต่ำถึงปานกลาง ขึ้นกับเนื้อหา error ของผู้ให้บริการและสิทธิ์เข้าถึง log
- **ตำแหน่ง:** `src/jobs.ts:188`, `src/affiliate.ts:236-242`, `src/line.ts:41-49`
- **สถานะ:** ยังไม่ยืนยันว่าข้อมูลส่วนตัวปรากฏใน error ของบริการจริง
- **ขั้นตอนที่ทำให้เกิดปัญหา:** จำลอง job handler ที่โยน `Error` ซึ่งมีอีเมล/ข้อความลูกค้าใน `message` จะเห็น `runJob` ส่ง error ทั้งก้อนไป `console.error`; ฝั่ง LINE เมื่อ API ตอบ non-2xx จะ log response body ทั้งก้อนเช่นกัน โค้ดยืนยันเส้นทางการ log แต่ยังไม่มีหลักฐานว่า Anthropic/LINE ส่งข้อมูลส่วนตัวกลับมาใน error response จริง
- **วิธีแก้ที่แนะนำ:** บันทึกเฉพาะรหัสเหตุขัดข้องและสถานะที่กำหนดไว้ล่วงหน้า แทน error object หรือ response body เต็ม และเพิ่มเทสยืนยันว่า log ไม่เก็บข้อความลูกค้า โทเค็น หรือข้อมูลติดต่อ

## สิ่งที่ตรวจแล้วและไม่พบช่องโหว่จากโค้ดที่อ่าน

- **Stripe:** `src/billing/stripe.ts` ตรวจ `Stripe-Signature` จาก raw body; `src/billing/index.ts:86-100` อ่าน Checkout Session จาก Stripe และเทียบ session ID, ยอด, สกุลเงิน, payment ID ก่อนให้เครดิต; `src/billing/index.ts:61-74` claim payment ด้วย `status='pending'` และ `apply_token` ใน D1 batch ทำให้ webhook ซ้ำสำหรับ **payment เดียวกัน** ไม่เติมเครดิตซ้ำ; `src/billing/index.ts:33-44,121-139` คำนวณราคาจากตาราง `plans` ฝั่ง server ไม่ใช้ราคาจาก browser
- **Auth:** session เป็น token สุ่ม เก็บ hash ใน DB และ cookie มี `HttpOnly`, `SameSite=Lax`, `Secure` เมื่อใช้ HTTPS (`src/auth/session.ts`, `src/auth/common.ts`); Google OAuth ใช้ state ที่ใช้ครั้งเดียว, PKCE และ `sub` จาก userinfo ที่อีเมล verified (`src/auth/google.ts`); reset token ใช้ครั้งเดียวและล้าง sessions หลังเปลี่ยนรหัส (`src/auth/password.ts`)
- **เครดิต/แอดมิน/API:** การ hold เครดิตตรวจยอดและบันทึกงานใน D1 batch (`src/jobs.ts:52-82`) จึงไม่พบเส้นทางหักเกินยอดจากการ enqueue พร้อมกัน; `/api/admin/*` ตรวจ bearer token ก่อนเข้าฟังก์ชันแอดมิน (`src/index.ts:97-106`); billing, works, receipts และ affiliate ผูกข้อมูลกับ user ID จาก session ก่อนอ่านข้อมูล (`src/index.ts`, `src/works/index.ts`, `src/receipts/index.ts`, `src/affiliate.ts`) ไม่พบการอ่านข้อมูลข้ามผู้ใช้จากเส้นทางเหล่านี้
